# 08 · 十阶怪物建模与陈列模式

> 起因是用户的一句抱怨：**"这不就是同一只放大了吗"**
>
> 改之前十阶共用同一套几何骨架（盒子躯干 + 盒子头 + 两只球眼 + 四条腿），
> 只换颜色和 `scale`。数值上十阶差 10.6 倍，观感上却是一只怪在做缩放动画。

### 关键设计点

1. **不是"换颜色"，是"换身体构造"**
   腿数（2 / 4 / 0）、有没有翼、有没有壳、是不是分节——这些是**结构性**差异，
   剪影就能分出来，不需要看清颜色。

2. **浮游种用起伏代替走路**
   T6 往后没有腿（或腿只是装饰），靠 `_model.position.y` 的正弦起伏表现"活着"。
   频率跟速度挂钩。

3. **相位延迟造出"波在传播"的感觉**
   分节躯干（T7/T9）每节的相位比前一节晚 0.62 弧度，
   看起来像一条波从头部传向尾部，而不是所有节一起摆。

4. **T10 用三头 + 光环立住"终极"感**
   三个头各自有独立的颈、头冠、发光眼，外加一圈缓慢自转的光环。
   这是玩家从 v1 就想要的"宇宙龙"该有的样子。

## 二、动画挂钩

`CreatureModel.build(tier)` 返回：

| 键 | 用途 |
|---|---|
| `root` | 模型根节点 |
| `legs` | 腿的 **pivot**（网格挂在 pivot 下面一半长处，从髋部转而不是从腿中间转） |
| `segs` | 分节躯干 / 尾鳍，做波浪摆动 |
| `wings` | 翼 / 鳍，做扇动 |
| `halo` | T10 光环，自转 |
| `float` | 是否浮游种 |
| `top` | 模型高度，用来决定 zZz 和头顶标签挂多高 |

统一由 `Creature._animate(speed)` 驱动，**所有频率都跟速度挂钩**：
- 摆腿 `sin(t × (4 + speed×0.55))`
- 体节 `sin(t × (2.2 + speed×0.30))`
- 扇翼 `sin(t × (1.8 + speed×0.22))`

→ 高阶怪不只是数值快，**看着就快**。

### `top` 为什么手写查表

标签高度需要知道模型有多高。算 AABB 理论上更准，但腿和翼是 pivot 包着网格的，
要处理多层变换；而这几个数字在摆模型时就已知，查表更简单也不会错。

## 三、陈列模式（`--gallery`）

```bash
# 从 T1 开始
"H:/.../Godot_v4.7.2-stable_win64.exe" --path . --resolution 1280x720 \
    --main-scene res://scenes/main.tscn --gallery

# 从指定阶位开始
... --gallery 7
```

操作：**按 `1`-`9` 直接跳阶，`0` 是 T10，`[` `]` 前后翻**，`ESC` 回农场。

陈列模式下怪物站着慢慢自转，不会追人也不会睡回去（`Creature.set_display(true)`）。

### 为什么一次只放一只，而不是一字排开

T10 体型 ×4.6、二十个单位高，十只并排根本塞不进画面；
就算塞进去，透视也会让远的那几只失真，反而比不出差别。

所以：**一次一只，观察距离按体型算** `z = -(6 + scale × 2.5)`
- T1（scale 0.8，高 1.9）→ 距离 8，占屏高约 16%
- T10（scale 4.6，高 20）→ 距离 17.5，占屏高约 79%

既看得清细节，又保住了体型差的冲击力。

## 四、建模自检

```bash
"H:/.../Godot_v4.7.2-stable_win64.exe" --path . --headless --script res://tools/model_test.gd
```

十阶各构建一次，打印网格数与动画挂钩：

```
  T1  草鸡    顶高 2.4 ｜ 网格 14 ｜ 腿 2 ｜ 体节 0 ｜ 翼 2 ｜ 光环 — ｜ 浮游 否
  T2  林蜥    顶高 1.4 ｜ 网格 18 ｜ 腿 4 ｜ 体节 3 ｜ 翼 0 ｜ 光环 — ｜ 浮游 否
  ...
  T10 宇宙龙  顶高 4.4 ｜ 网格 37 ｜ 腿 0 ｜ 体节 0 ｜ 翼 6 ｜ 光环 有 ｜ 浮游 是
[建模自检] 合计网格 216，最重的是 T10（37 个）
```

### ⚠️ 为什么需要这个脚本

`--jump 20000 --diag` 看着覆盖了高阶，**其实怪物列表在传送之前就生成完了**，
不管跳多远，阶位分布始终是 `{1..7}`，T8/T9/T10 的建模代码压根没跑到。
只有这个脚本是真的逐阶构建。

### ⚠️ 为什么它不实例化 creature.tscn

`--script` 模式**不会把 autoload 注册成全局标识符**，
`creature.gd` 里引用的 `GameEvents` 会编译失败（`Identifier not found`）。

所以自检只测 `CreatureModel.build()`（它只依赖 `CreatureDB`）。
`creature.gd` 那边的接线由 `--gallery N` + headless 覆盖。

### 另一个坑：`find_children` 的 `owned` 参数

```gdscript
root.find_children("*", "MeshInstance3D", true, true)    # ← 返回 0 个！
root.find_children("*", "MeshInstance3D", true, false)   # ✅
```

运行时 `add_child()` **不会设置 owner**，第四个参数传 `true` 会一个都找不到。
第一版自检就是这么报出"网格 0"的假象。

## 五、性能预算

单只怪 14–37 个 `MeshInstance3D`，平均约 22。
单局 84 只怪，但 700 单位外的睡怪 `visible = false` 且跳过 `_physics_process`，
实际同屏通常十几只 —— 约 200–400 draw call，可接受。

超过 40 个网格自检会打警告。T10 目前 37，接近上限。

**如果要继续加细节，优先加在低阶**（低阶同屏数量多但网格少），
或者给高阶做 LOD。
